# Valentte Email Production Workflow

**Before doing any work, also load [references/project-history.md](references/project-history.md)** — it has the accumulated state from prior sessions: which Bloomreach campaigns already exist and their exact ids, which Figma page/frames already exist and their node ids, and what's already been decided vs. still open. Don't rebuild something that's already there; check the history first.

Valentte's real, already-sent marketing emails use a "stitched images" method: a designer builds each section as a flattened image with text baked directly onto the photo (headline, badge, CTA all part of one PNG), then a freelancer assembles those image blocks in Bloomreach. This skill covers the **coded alternative**: reproducing the same visual result using live HTML/CSS text wherever possible, and only baking text into an image where the original genuinely does that (hero banners, offer-of-the-day style sections).

## The four tools in play, and why each is there

- **Bloomreach Engagement ("Loomi Connect")** — the campaign platform. Emails live as `email_campaign` objects with a `jinja_html` blob. **Bloomreach has no image-upload API** — this is the whole reason Higgsfield is in the pipeline (see below).
- **Figma** — used for three things: (1) building B&W wireframe templates (structural references, no real copy), (2) compositing baked-text-on-photo banners exactly like the brand's existing flattened-image style, and (3) as a general-purpose image-cropping tool (see "Cropping without external tools" below) — it can extract an exact pixel sub-region out of any larger image via an image fill's `imageTransform`, which is more reliable than eyeballing a crop in an external editor.
- **Dropbox** — the canonical source of real, approved Valentte brand photography. Two folders, confirmed browsable directly via the connected Dropbox account (`list_folder`/`get_file_content`), and this should be the **default first place to pull a real product photo from** — both for a normal "get me an image of X" request, and as the reference image fed into Higgsfield for any Tier-2 reference-edit generation (see the Higgsfield section below):
  - **`/Valentte's shared workspace/Email Marketing/2026 Email Marketing/Templates/AI raw`** — the older, more curated library (~22 subfolders: Gift Boxes, Perfume, Candles, Diffusers by count, Hamper, Decorative Backgrounds, Collections, etc.)
  - **`/Valentte's shared workspace/x- temp email images`** — a much larger, actively-maintained library (~45 subfolders, most added within the same day), covering nearly every product line by name (Body Scrub and body butter, Reed Diffusers, Gift Boxes, Hand Cream, Candles, TikTok images, seasonal collections, etc.) — check here first for anything product-specific, it's the fresher/more complete of the two.
  - **`create_shared_link` output is private / team-authenticated-only** — verified by curling it and getting Dropbox's login HTML back, not image bytes, even with `dl=1`. That's only a problem if you need a *public* URL (e.g. hosting a finished asset for Bloomreach) — go straight to Higgsfield for that. It is **not** a problem for browsing/downloading files from these folders via the authenticated `dropbox` MCP connection to use as a local reference or generation input.
- **Higgsfield** — two genuinely different jobs, don't conflate them:
  1. **Public image host** (original use): `media_upload` → PUT the bytes to the presigned URL it returns → `media_confirm`. The resulting CloudFront URL is what actually goes in the email HTML's `<img src>`. Works for *any* file, including ones built entirely in Figma with no AI involved.
  2. **AI image generation** (added later — see the dedicated section below): `generate_image` with model `gpt_image_2_5`, used to elevate real product photography or generate decorative/background imagery. This is a much higher-risk capability than the plain host use — read the section below before using it, it has already caused real content bugs in this project.

## Decision rule: baked-text-on-image vs live HTML text

Look at the actual original/reference email section:
- **Text sits directly on top of a photo** (hero banners, "Offer of the Day" gift-box sections, review/testimonial sections with a photo background) → build it as ONE flattened image in Figma, upload via Higgsfield, reference it as a single `<img>` in the HTML. Do NOT try to overlay live HTML text on a background-image `<td>` — that's not how these brand sections are actually built, and it won't match.
- **Text sits on a flat solid-color background, or beside a photo (two-column image-left/text-right layout)** → write it as live HTML/CSS text. This is editable, faster to update, and matches sections like the top promo strips and the Christmas Hamper block.
- When in doubt, check the real, already-sent reference email for that flow step and match its actual construction — don't guess.
- **This rule now also answers "can Higgsfield replace the photo half of this equation?"** — yes for the *photo*, but the *text* should still be typeset for real in Figma (or live HTML) and flattened together, never left to the AI model to render. See "Never let the model render text or logos" below — this was tested directly and the model is not reliable at it.

## Higgsfield AI image generation — read this before generating anything

This is separate from Higgsfield's plain image-hosting role above. Generation is genuinely useful for making emails look more premium (elevating real product photography, generating mood/background imagery, custom icon sets) — but it has caused real, shipped-adjacent bugs in this project. Follow this section exactly.

### Model, cost, and tracking discipline
- Use `generate_image` with `model: "gpt_image_2_5"`, params `quality` (`low`/`medium`/`high`/`xhigh`/`max`) and `resolution` (`1k`/`2k`/`4k`). Confirmed pricing: low/1k = 0.25 credits, medium/2k = 1 credit, high/4k = 4.25 credits. On-demand rate ≈ 18 credits per $1.
- **Attaching a reference image via `medias` does NOT change the cost** versus a blank-slate generation at the same quality/resolution — confirmed empirically with `get_cost: true`. There's no cost reason to avoid reference-based editing.
- **Never track spend by diffing the account `balance`** — other operations may be drawing on the same shared account concurrently, so a balance diff is not attributable to your own work. Track spend by summing your own `get_cost`/per-generation costs directly as you go, and compare that running total against whatever ceiling the user gave you.
- If `balance`/`list_workspaces` shows the wrong plan or an unexpectedly low balance, the Claude-side connector may still be bound to a stale browser session. Disconnecting the Claude connector alone does **not** clear it. Fix: log out of higgsfield.ai in the browser first, *then* disconnect/reconnect the Claude connector.

### Never let the model render text or logos — verify every generation by eye
This is the single most important rule in this section. Across this project, **every single time** a reference image containing real brand text or logos was fed into `generate_image`, the model had a real chance of corrupting or inventing text near it, even with an explicit reference image meant to anchor it in place. Confirmed failures, not theoretical risk:
- A jar label edit added a fabricated scent-name line that wasn't on the real product, and got the scent wrong.
- A packaging-box texture edit corrupted "VALENTTE LONDON" into "VALL'NTTE LONDON" mid-generation.
- A retry of that same box fabricated a "www.valentte.com" URL that doesn't exist on the real packaging.

None of these were caught by the prompt alone (all three generations *did* include explicit "keep the label exactly as shown, do not alter the text" instructions) — they were only caught by **looking at the actual output image before using it**. So:
- **Always view every generated image yourself before wiring it into Figma or an email.** Never chain a generation straight into an upload without a look.
- If a reference image contains real product/brand text, expect to need 1–2 retries with even more explicit constraints ("do not add any text or wording not already present in the reference image") before it comes out clean.
- If it's still wrong after a retry, don't keep spending credits hoping — either crop the specific text-bearing region out of the *real* photo instead (see cropping section below) and generate around it, or accept the real, unedited photo for that element.

### The three-tier content-risk rule
Use this to decide, up front, whether a given piece of email content is even a candidate for AI generation:
1. **Safe to blank-slate generate freely**: pure decorative/background imagery with no product, no text, no logo — mood photography, linen/fabric textures, abstract backgrounds, generic line-icon concepts (delivery van, customer-care headset, UK-made ribbon, referral heart-bubble). These have no brand-accuracy risk at all.
2. **Reference-edit only, never blank-slate, always verify**: anything that must show the *real* product, jar, packaging, or wordmark. **Pull the source photo from the two approved Dropbox folders above first** (see the Dropbox bullet), rather than screenshotting whatever happens to already be in Figma — that's the actual canonical asset library, not a side effect of prior wireframe work. Use the real photo as a `medias` reference (role name varies by model — check `models_explore(action:'get', model_id:...)` for the exact role, e.g. `image_references` for `gpt_image_2_5`), prompt for scene/lighting/styling changes only, and explicitly forbid any text changes. Verify by eye per the rule above.
3. **Never generate, ever**: payment method logos, legal/compliance text, physical addresses, unsubscribe mechanisms, exact approved proof-point wording. These must always be either a cropped real image or live, typed text — never AI output. This isn't a style preference, it's a compliance/accuracy floor.

### Cropping without external tools
Figma's own image-fill system can extract an exact pixel sub-region from any larger image, which is more reliable than eyeballing a crop in an image editor and doesn't need any external tooling:
```js
rect.fills = [{
  type: "IMAGE", scaleMode: "CROP", imageHash: hash,
  imageTransform: [[(x1-x0)/W, 0, x0/W], [0, (y1-y0)/H, y0/H]]
}]
```
where `x0,x1,y0,y1` are the pixel bounds you want out of an image of size `W×H`. Upload the source image once with `upload_assets` (no target node) to get an `imageHash`, then apply this transform on as many rectangles as you need. Verify the crop bounds with a quick test rectangle + `get_screenshot` before committing to the final position — cheap to iterate, and catches off-by-a-few-px errors before they're baked into a real asset.

This is also how to build a hybrid "safe" version of a content-dense section (e.g. an email footer with payment logos + legal text): crop the risky sub-strips (payment icons, legal copy) directly out of the real accurate source image, and only regenerate or restyle the surrounding decorative elements.

**Anti-pattern, confirmed by a real regression**: don't trust ad-hoc local rendering tools (e.g. macOS QuickLook thumbnailing of an SVG or HTML file) as a source of pixel-accurate reference images for cross-client email fallbacks. QuickLook's internal scaling was inconsistent between an SVG-only render and an HTML-page render of the same content, producing a fallback image that didn't match the real shape and caused a visible regression when shipped. If a pixel-perfect local render is genuinely needed and no proper headless-browser tool is available, say so rather than shipping an unverified guess.

## The Figma → Higgsfield → Bloomreach round-trip

1. **Build/edit in Figma** via `use_figma` (load the `figma-use` skill first, every time — either `/figma-use` or the `skill://figma/figma-use/SKILL.md` MCP resource).
2. **Match the curve type to what's actually in the source — don't default to the S-curve everywhere.** Two genuinely different shapes show up in Valentte references: a true **S-curve** (hill then valley, two lobes — used for section-to-section dividers) and a single **arc/U-curve** (one smooth dip, like a photo with an arched bottom edge — used for circular/arch-masked hero photos). Check which one the reference actually has before building; don't reach for the S-curve boolean-subtract technique just because there's *a* curve. A single arc is simplest as a big ellipse (roughly frame-width-plus-60px wide) positioned so only its bottom portion peeks into the frame — no boolean op needed, since there's no adjacent same-color shape to seam against.
3. **Wave/curve section dividers: use boolean-subtract, never an overlapping same-color vector.** A separate vector shape filled the same color as the page background (e.g. a white wave "cut" sitting on a white page) reliably renders a visible gray seam artifact at its edge in Figma's PNG export, even with strokes/effects fully cleared — this is a rendering quirk, not a paint-property bug. Instead: create the block rectangle at full size, create a second "cutter" vector using the wave path (a genuine two-lobe S-curve — hill then valley, pronounced amplitude, not a flat/subtle curve), position it overlapping and extending a few px *past* the block's true edge, then `figma.subtract([block, cutter], parent)`. Re-apply the block's fill color to the result explicitly, and watch z-order — `subtract`/`union` append the result to the end of the parent's children (in front of everything), so immediately `parent.insertChild(idx, result)` back to where the original block sat if there's text that needs to render on top of it.
4. **If elevating real product photography with Higgsfield, do it before export** — see the dedicated Higgsfield section above for the reference-edit + verify-by-eye workflow.
5. **Export**: `download_assets` or `get_screenshot` (maxDimension high enough for retina — these are display images, not thumbnails).
6. **Upload for public hosting**: `media_upload` (Higgsfield) → the response gives a presigned S3 PUT URL per file → `curl -X PUT -H "Content-Type: image/png" --data-binary @file.png '<url>'` → then `media_confirm` with the returned `media_id`(s). The `url` field in the original `media_upload` response (a `d2ol...cloudfront.net/...` URL) is the permanent public URL — verify it with `curl -sI` before trusting it (expect `HTTP/2 200`).
7. **Wire into Bloomreach**: see below — this is where mistakes are expensive.

## Bloomreach `update_email_campaign` — the part that can silently destroy a live campaign

- **The tool may not appear in your default tool list.** If so, it's not missing — call the Loomi server's own `search_tools` with a query like "update email campaign", then invoke the result via `call_tool(name, arguments)`. Same applies to other less-common Loomi tools (e.g. `generate_email_campaign_preview_link`).
- **Always fetch first with `include_design=True`.** The default (`False`) strips `jinja_html` from the response specifically to save tokens — feeding that stripped object back in deletes the email body.
- **The top-level `design` field is authoritative on write; the backend rebuilds `split` from it and ignores whatever is inside `split.variants[].design`.** Mutate `payload['design']['data']` and mirror the *exact same* value into `split.variants[0].design` so they never disagree. Editing only inside `split.variants` has no effect and the call still reports success — a trap that looks like it worked.
- **Before sending, re-read your own payload and sanity-check that `jinja_html` is the real, full HTML** — not a placeholder, not a truncated stub, not literally the string `"PLACEHOLDER"` or similar. Because these payloads are huge, it is very easy to have a stray edit leave a field as a short debug value while everything else looks fine. This has actually happened in this workflow before and briefly wiped the live campaign body; it was only caught by immediately re-fetching and checking. **Treat every `update_email_campaign` call as: construct → visually re-scan the actual field value for suspicious shortness → send → re-fetch with `include_design=True` → confirm the new image URLs / content are actually present in both `design.data` and `split.variants[0].design.data`.**
- **For any edit to an existing large `jinja_html` blob, don't hand-retype it.** Write the current fetched HTML to a local file, apply the change with `sed`/a small script, `diff` the before/after to confirm *only* the intended lines changed, and only then read the file back into the update payload. This caught zero-error edits reliably across many rounds of real edits in this project — manually retyping a 10–15 KB HTML blob is exactly how a stray character silently breaks a live template.
- Never drop or rename fields you don't recognize when carrying a fetched payload forward (e.g. `transfer_user_identity`) — every field absent from the payload is reset to its default, not left alone.
- If you need to change one small thing and are unsure of blast radius, do the edit, then immediately offer (or do, if already instructed) an undo path back to the exact prior state — keep the pre-edit HTML around until the change is confirmed good.

## Permanent rule: link identity transfer = "Enabled (only first click)"

Every email put into Bloomreach — one-off campaigns, scenario/flow email nodes, and hand-built raw-HTML emails — must have **Transfer identity to URL links** set to **Enabled (only first click)**. In API payloads that is `transfer_identity: true` and `transfer_user_identity: "first_click"`.

- **Never "Disabled".** Clickers land on site anonymous: they get new-visitor pop-ups instead of their real offer, and basket/attribution don't link back. This happened on Evening Email 28/10/26 (raw HTML, defaulted to disabled) and it converted at a quarter of the previous night's rate.
- **Never "Enabled (all clicks)".** Every link stays an identity token, so a forwarded or shared email can tie someone else's browsing to the customer.
- **Raw-HTML / hand-built emails do not inherit this from the BEE template** — set it explicitly, and check it before scheduling, on every send.

## Footer & link-integrity checklist — run on every email, every footer

Hard-won from fixing four real cart-abandon-flow emails (Email 1 "Cart Abandon · Short", Email 2 "Founders", Email 3 "Mystery Gift", Email 4 "Last Chance") where several of these were live in production with broken links nobody had caught. Run this checklist on **any** footer you build or review — these are generalizations, not one-off fixes scoped to those four emails.

- **Anchor-tag balance.** Count `<a ` opens vs `</a>` closes in the full HTML before shipping — they must match exactly. An unclosed anchor can silently break rendering in some tools (confirmed: it made Bloomreach's own design-preview editor drop a social icon entirely) even when real email clients tolerate the malformed markup and show it fine. Don't eyeball this, count it.
- **`display:block` is required on every link wrapping block-level content.** An `<a>` wrapping a `<table>`, multiple stacked elements, or an image needs `display:block` in its inline style — `text-decoration:none` alone, or `display:inline-block`, is not sufficient. Confirmed root cause of a real "the logo isn't clickable" bug reported from an actual received email, even though the href itself was correct and the link looked fine in a browser/preview tool. This is specifically a known Outlook/Word-rendering-engine failure mode.
- **Footer row width math must sum to the container's full width.** For any footer built from sliced/cropped images in a row (icon rows, payment-logo rows), add up the cell widths and confirm they total exactly the container width (e.g. 600px) — don't assume the designer's slices add up correctly. A mismatch causes visible bunching/misalignment on one side of the row. (Confirmed real bug: a social-icon row summed to only 479px instead of 600px.)
- **Multi-cell "sentences" must share one destination.** When a line of text/instruction is split across multiple adjacent image cells (e.g. "Change your contact preferences" + a separate tiny "here" image), every cell in that visual line must link to the identical destination. Never let adjacent cells in the same sentence silently diverge — a customer has no way to tell where exactly they're clicking.
- **Every visually-clickable element must actually have a link — don't assume decorative.** Explicitly check: logo → homepage; nav links → their most specific matching page, not a generic parent page; checkout/trust-badge images → cart page; "Change your contact preferences" → same destination as Unsubscribe (`{{ email.unsubscribe }}`); social icons → their real URLs; "View in Browser" → `{{ email.view }}` (kept distinct from contact-preferences, never conflated); Unsubscribe → `{{ email.unsubscribe }}`. Ask this question on every footer, every time: "does every element that looks like a button/icon/link actually have a working `<a>`, and does it go to the right place?"
- **Jinja null-safety — check every conditional, every section, not just names.** `default()` only replaces truly *undefined* Jinja values — it does **not** catch an explicit `null`. If a customer property is stored as explicit null (not simply missing), `property | default('') | trim` lets the null through, and `trim` stringifies it into the literal text `"None"` — which then reads as a real (wrong) value in any truthy check. Confirmed real bug: "Hi None," greeting shipped to a real inbox. Fix pattern: `(property or default) | filters`, e.g. `(customer.first_name or '') | trim` — never rely on `default()` alone. Apply this check to every personalization token in every section (greetings, cart totals, event titles, anything customer- or event-sourced), not just the one that broke.
- **Never trust Bloomreach's manual "test send" / preview-link tooling to validate event-bound content.** It never populates real `event.*` Jinja tokens (cart quantity, cart total, etc.) under any circumstance — only a genuine live-triggered event does. Any claim that personalized/event-bound content "works" must be verified against a real triggered send, never a manual test send or preview link.
